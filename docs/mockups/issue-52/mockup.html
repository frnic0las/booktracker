Issue #52 — Account hero stat

The Account hero currently carries one number: Total books. The stats API now also returns totalPagesRead (completed, non-abandoned books only). This board picks a layout for the second number, fixes its type scale, and specifies the states. No new design token is introduced — every value below already exists in src/app/globals.css.

Board 1

Split hero Recommended

One card, two columns, one hairline. The hero stays a single object in the layout, so the page still opens on one hero and then the two category lists. Both numbers sit on a shared baseline; Pages read reads as the lesser of the two through size (28px vs 36px), weight (700 vs 800), and colour (--secondary vs --primary) — three signals, no new colour.

Board 2

Two free-standing cards Rejected

The issue's second option, rejected on hierarchy. Two identical side-by-side cards say the two numbers matter equally, which contradicts the brief — and they break the page's rhythm of one hero, then two lists. The width cost is real but minor: a 12px gutter and two extra borders take each column's content from 137.5px to 131.5px at 375px. Six pixels would not decide this on its own. Shown here for the record.

Board 3

States

totalPagesRead is a SUM over books.page_count, which is nullable in the schema and absent from plenty of Google Books volumes. A user with 40 finished books can still legitimately see 0. The zero state is therefore a normal state, not an empty state: it keeps the number, the label, and the card geometry. Nothing is hidden, nothing collapses.

Why the numbers are grouped. 8420 renders as 8,420 via Intl.NumberFormat. Page counts run four to six digits and an ungrouped 412880 is measurably slower to read. The column is also set in tabular-nums so the digits do not shift width between renders.

Overflow. The Pages read cell has 137.5px of content width at 375px (343px card − 2px border − 32px padding − 1px rule, halved). Six digits plus a comma at 28px tabular runs roughly 110px, so 412,880 fits with room left — the specimen above is here to be checked in a browser rather than taken on trust. The layout does not truncate or wrap: the cell is min-w-0 with whitespace-nowrap, and the grid gives each column a hard 1fr, so a runaway value overflows the card rather than crushing its neighbour. Seven digits (a million pages — roughly 3,000 finished books) is out of range for a single-user library, and no defensive truncation is specified for it.

Board 4

Viewport range

The card is fluid; only its inner columns change width. At 430px the two numbers drift further apart, which is exactly what the hairline is there to hold together.

Board 5

Both themes

Dark is primary. Light is the same markup with the light token set — no class in the component names a colour literal, so nothing needs a dark: variant.

Pre-existing contrast debt, not introduced here. The Total books label already uses --tertiary, which measures 3.42:1 on dark and 2.30:1 on light against --surface-1 — under the 4.5:1 that WCAG AA asks of 13px text. Pages read inherits the same label style for consistency, so this issue neither worsens nor fixes it. Raising every label to --secondary would in fact clear AA in both themes (7.05:1 and 4.73:1), but it touches every section label in the app and belongs in its own issue. The stat values are fine: --secondary at 28px/700 measures 7.05:1 dark and 4.73:1 light — past AA for normal text, never mind the 3:1 large-text threshold it only has to meet.
